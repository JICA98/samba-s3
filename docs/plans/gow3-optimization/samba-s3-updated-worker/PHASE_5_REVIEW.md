# Phase 5 independent review — prime-core rendering affinity (2026-09-25)

## Verdict

**Partial implementation; reject the word “exclusive”; throughput and Gaia benefit unproven.** Alternative Scheduler computes an affinity preference for the RSX CPU thread, not a reservation of the highest-frequency CPU for all frame rendering. The existing `RPCS3 Scheduler` performance-core mask remains the CR04/Gaia control (`WORKER.md:310`; `PHASE_EVIDENCE_AUDIT.md:39`). Do not substitute Alternative Scheduler into that matrix without a separate controlled experiment. This review changed no scheduler or device state.

## Findings, ordered by impact

1. **P1 — No exclusive reservation.** `rpcs3/util/Thread.cpp:3249-3288` gives RSX `prime_mask`, SPU/PPU `performance_mask & ~prime_mask`, but `general` threads retain `allowed_mask` (`:3282-3285`). `:3222-3240` lets explicit custom affinity override the entire policy. Android UI, driver, kernel, other applications, system services, and emulator workers outside the classified CPU/RSX entry points are not excluded. `sched_setaffinity(0, ...)` affects only the calling thread (`:3659-3675`); it does not reserve a CPU or control other processes. Rewrite the claim as “prefer/pin the classified RSX thread to the discovered prime mask, subject to cpuset and successful syscall.”

2. **P1 — “Highest-frequency” is conditional, not guaranteed.** Discovery prefers `cpu_capacity` over `cpuinfo_max_freq` (`Thread.cpp:2925-2984,2987-3047`). The capacity maximum can include multiple equal-capacity CPUs despite distinct frequency ceilings; `prime_mask` then contains several CPUs. The frequency path likewise includes every CPU tied at maximum (`:3010-3036`). MIDR fallback recognizes selected Cortex-X parts but is not a frequency ranking (`:3049-3104`). The midpoint performance/efficiency split and minimum spread checks (`:2941-2944,3003-3006`) can classify a three-tier device imperfectly. `prime_mask` is deliberately cleared if it equals all performance CPUs (`:2972-2979,3034-3041,3093-3100`); homogeneous/unclassifiable topology has no prime (`:3107-3113`). Thus the code cannot promise one fastest CPU on every handset.

3. **P1 — Renderer classification is narrower than frame rendering.** The RSX entry calls `get_affinity_mask(thread_class::rsx)` at `rpcs3/Emu/RSX/RSXThread.cpp:1082`; guest CPU entry uses its own class at `rpcs3/Emu/CPU/CPUThread.cpp:640`. RSX GPU driver submission, Vulkan driver threads, presentation/compositor and app/UI threads are not established as RSX-class by these calls. Restricting this one CPU thread may help CPU-side RSX work yet does not guarantee frame completion latency or GPU throughput. Confirm thread identity and the actual critical path before calling it a render-core policy.

4. **P1 — Allowed-mask snapshot and failure handling prevent a runtime guarantee.** `get_process_affinity_mask()` caches the current calling thread's affinity once (`Thread.cpp:3574-3599`), and topology is likewise cached (`:3116-3197`). A calling thread's mask is not a process-wide cpuset contract; later cpuset changes, restore/new threads, and differing inherited masks can invalidate the cached snapshot. `get_affinity_mask()` intersects a fresh call with cached topology (`:3323-3326`), but that call returns the same cached mask. `set_thread_affinity_mask()` intersects with the cached mask (`:3618-3637`), reports syscall errors (`:3659-3670`), and does not retry, read back, or revert to the full currently allowed mask on failure. A zero allowed mask in the arithmetic helper becomes `topo.allowed_mask` or hardcoded `0xFF` (`:3207-3210`); production discovery instead derives a hardware-concurrency fallback (`:2913-2917,3592-3594`). Neither fallback proves a legal cpuset. Log requested, kernel-effective and read-back masks per TID; recalculate from current kernel state when launching/relaunching threads.

5. **P2 — Alternative can reduce throughput.** On a Snapdragon layout with `allowed=0xff`, `perf=0xfc`, `prime=0x80`, Alternative assigns RSX `0x80`, SPU/PPU `0x7c` (`Thread.cpp:3252-3281`); old RPCS3 mode assigns all three `0xfc` (`:3291-3305`), while OS mode returns the full allowed set (`:3242-3247`). That trades scheduler flexibility and five-or-six-way SPU/PPU contention against a potentially less contended RSX CPU. Prime-only RSX may stall on driver waits while unused cycles go elsewhere; SPU/PPU loss of the prime can starve the FIFO. Thermal and cpuset changes can reverse any gain. No measured frame-time or Gaia progression comparison validates the trade.

6. **P2 — Historical OS-mode crash does not establish Alternative success.** `PHASE_EVIDENCE_AUDIT.md:39` says OS failure shows timing sensitivity, not a Little-core hardware defect; `WORKER.md:504` demands synchronization/starvation investigation. Historical E03 OS evidence and the existing `PHASE_5_REVIEW.md` predecessor describe a dead FIFO and indirect scheduler logs, not an Alternative-mode device trial. `WORKER.md:465` specifically requires actual affinity and capabilities for relevant restored/new threads after SIGILL. Keep `WORKER.md:310`'s performance-core control throughout CR04 A–D; do not reinterpret an OS-mode failure as proof of prime-only improvement.

## Verification and evidence boundary

- `python3 -m unittest discover -s scripts/tests -p test_cpu_topology.py -v`: **25 passed** on this review. `scripts/tests/test_cpu_topology.py:511-519` compiles/runs the standalone C++ test and asserts its **24** checks passed. These are mirrored topology/mask implementations (`scripts/tests/test_cpu_topology.cpp:36-43`), not a native build or invocation of production `Thread.cpp`, kernel cpuset, or live thread readback. They cover synthetic masks, modes, and fallback, not CPU/GPU frame latency.
- Repository benchmark logs contain topology announcements (e.g. `docs/benchmarks/gow3-run.log:2036`), but no demonstrated Alternative-mode run with matched per-TID affinity readback and frame/thermal measurements. A topology log only demonstrates discovery; successful `sched_setaffinity` is trace-level (`Thread.cpp:3671-3675`), not a readback. Historical E03 is OS mode. No new launch, install or device mutation performed for this review.
- The submodule has uncommitted changes in `rpcs3/util/Thread.cpp`, `rpcs3/util/Thread.h`, and `android/src/rpcsx-android.cpp`; the review assesses working-tree code, not a proven released binary. Existing untracked/modified benchmark documents were preserved.

## Exact corrective steps and acceptance measurements

1. **Correct scope and topology:** Remove “exclusively” from `Thread.cpp:3249-3251` and any product claim. If the requirement is one highest-**frequency** CPU, choose exactly one allowed online CPU by verified max-frequency with documented capacity/MIDR fallback and tie-breaking; otherwise state explicitly that the prime set can be multi-core and unavailable. Test partial/missing topology, ties, three-tier clusters, restricted cpusets, dynamic mask changes, custom overrides, and `prime_mask=0` against the compiled production helper.
2. **Verify application, not just computation:** For each relevant thread creation/recreation, record TID, name/class, mode, current `sched_getaffinity`, requested mask, `sched_setaffinity` errno, and subsequent readback. Resolve fresh cpuset/online mask when applying the setting; on failure keep scheduling operable on the kernel-allowed mask and report the fallback. Include RSX, SPU, PPU, general, UI and Vulkan/driver threads in the audit. Observe permitted `/proc/self/task/<tid>/status` from inside the app if host `/proc/<pid>/task` is denied; do not infer success from topology logs.
3. **Controlled comparison after CR04:** Preserve `RPCS3 Scheduler`/`0xfc` as the OnePlus control through the `WORKER.md:310` Gaia A–D matrix. Once progression is stable, compare old, Alternative and OS modes on the same game/build/driver/settings, fixed G1 combat, G3 transition and G6+ route, same thermal starting band, repeated runs. Record PID/build hash, topology and per-TID allowed/effective masks, CPU residency and run-queue delay, RSX FIFO stalls, GPU busy/present timing, thermal/frequency traces, frame count, median/P95/P99/max frame time, >33/>50 ms stalls and successful G2–G7/save-load progression. Report per-run distributions and uncertainty (`WORKER.md:563,597`); accept only a reproducible improvement without regression in throughput, correctness, or Gaia progression. Investigate FIFO producer/consumer starvation if Alternative increases stalls (`WORKER.md:504`).
