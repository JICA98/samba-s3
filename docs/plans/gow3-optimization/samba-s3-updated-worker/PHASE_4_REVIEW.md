# Phase 4 independent review — 2026-09-25

## Scoped verdict

**PARTIAL / retain provisionally.** Phase 4 means logging/frontend overhead, not Gaia route recovery (`PHASE_EVIDENCE_AUDIT.md:33-44`; `WORKER.md:13,254,571`). The previous `VERIFIED_FOR_DECLARED_SCOPE` verdict in `docs/performance/gaia-recovery-status.md:17,32` and the former version of this review overstate diagnostic completeness and measured overhead. No evidence here establishes Phase 4 as the cause of the Gaia failure. No code or device state changed in this review.

## Findings (priority order)

1. **P1 — Crash-record durability is not guaranteed.** `LogMonitor.kt:222-230` classifies critical entries, but `:343-356` normally queues them; synchronous processing happens only when enqueue fails. Writer `flush()` (`:400-411`) is not an `fsync`, and `flushPendingWriters()` suppresses I/O exceptions (`:300-307`). `stop()` cancels the consumer before closing the channel (`:259-271`), so queued entries need not drain. Upstream `logging/LogBroker.kt:43,81,92,99` counts dropped broker entries. Focused tests demonstrate selected immediate-write cases, not losslessness across broker saturation, abrupt death, and shutdown. The former F04-1/F04-2 and “no diagnostic truncation” conclusions are unsupported.
2. **P1 — The cited historical bundle does not prove zero overhead or complete logs.** `docs/benchmarks/evidence-e03-f04-logging-frontend/run-manifest.json:25,34` names a thread snapshot and backend log. Existing bytes and a low sampled `Log Writer` CPU figure establish capture, not equality to a source stream or continuous CPU utilization. A single `threads-top.txt` observation cannot rule out bursts, blocked queues, or missing fatal tail. The former review's 12 MB/126,540-line argument was a count, not an integrity comparison.
3. **P2 — UI coalescing has a qualified ceiling.** `LogMonitor.kt:322-340` clones `allBuf` even without subscribers; `:351-356,363-368` forces publication on critical fallback. Thus “only with subscribers” and a strict 300 ms ceiling do not follow from the code. Retain the optimization as bounded typical-path behavior, not universal cadence or zero allocation.
4. **P2 — Controller axis mismatch is a testable hypothesis, not a demonstrated Phase 4 failure.** `ui/ingame/GameplayInputGate.kt:48-67` reads raw X/Y/Z/RZ and trigger pairs, then requires physical neutrality; `:97-112` blocks input until a subsequent event satisfies it. `input/ControllerProfile.kt:57-69,305` defaults right stick to Z/RZ but allows profile bindings; `input/GamepadMapper.kt:102-114` consumes those configured bindings. `RPCSXActivity.kt:2283-2306` updates tracker before gate and mapper. A remapped controller could therefore move on an axis ignored by the neutral tracker, or a raw axis could hold the gate closed. No per-device axis/profile trace or gate-state timeline in the cited bundle proves either scenario. A stuck image alone cannot distinguish this from guest stall.
5. **P2 — Later interactive death is not a proven emulator crash.** `docs/benchmarks/evidence-cr02-interactive-20260925-132400/session-summary.md:3-16` reports `PROCESS_DIED`, PID 579, SIGNALED status 9, and no interactive FPS. SIGKILL does not identify the killer or prove SIGSEGV, input causality, or the Gaia route. `docs/performance/gaia-recovery-status.md:6-7,15` still marks the route blocked/CR02 not reached; later artifacts require their own reconciled timeline before revising that ledger.
