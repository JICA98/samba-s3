The revised isolated build script was inspected, not inferred from the worker's result. Its explicit --check-patch-guard path invokes only the patch check and exits before toolchain lookup, submodule initialization, build-ID stamping, or compilation. For an already-applied persistent patch it reverse-checks every retained hunk; for an unapplied patch check-only returns failure without applying it. Normal release no longer reads RPCSX_PATCH_GUARD_ONLY, so the old false-success route is gone. In normal mode, a forward check precedes application and a patch that is neither fully forward- nor reverse-applicable fails. Filtering the generated samba-build-id.cpp section now rejects a **nonempty** patch with no persistent hunks. An actually empty or absent patch remains the pre-existing no-op behavior; the pinned source manifest records a nonempty patch hash, so the next build task must verify that exact source input rather than rely on the no-op case.

I inspected the focused test source and its recorded passing command log. The tests cover applied check-only with unchanged app/core/build-ID/script hashes, forward application, legacy-variable release reaching a deliberately failing CMake shim (exit 97, not success), stale persistent-hunk rejection before stamping, nonempty generated-only rejection, and empty-patch no-op. The shim stops each release-path fixture before compilation. These are meaningful control-flow tests, not a successful core build; I did not rerun them under this review's no-build constraint.
